## Product and design

Build a local-first Android app that discovers and controls arbitrary ESPHome Native API devices directly, without Home Assistant, a cloud service, MQTT, or a required backend. Discover entities dynamically and use advertised capabilities and protocol message types, never infer controls from names. `screen1.png` and `screen2.png` are early visual references. The user wants separate homes, assigning discovered devices to the selected home, settings, and a home dashboard with device controls. Read-only values belong to the right of their entity names, aligned like control widgets.

## Implementation map

- Kotlin, Jetpack Compose, Android NSD, Gradle; application ID and namespace `com.example.esphomecontroller`. Minimum Android API 26, compile/target API 35. The current Noise dependency supports encrypted connections only on API 33+; keep that limitation explicit until a compatible implementation is verified.
- `app/src/main/java/com/example/esphomecontroller/MainActivity.kt`: activity and foreground discovery, serial NSD resolution, lifecycle and multicast lock.
- `HomeScreen.kt`: Compose screens, locally persisted homes/device assignments, device setup/editing, foreground automatic connection and retry orchestration, theme preference, and entity tiles. `HomeStore` currently uses SharedPreferences; it is not Room.
- `api/DeviceSession.kt`: per-device socket session, protocol dispatch, reactive UI state, and initial commands. `api/EntityCache.kt` retains control metadata and last reported state only in a ViewModel in memory, across temporary disconnects and activity recreation; never persist those states to disk. `api/NoiseFrames.kt` and `api/PlaintextFrames.kt`: encrypted and plaintext framing. `api/SecretStore.kt`: Android Keystore-backed AES-GCM storage of device keys. App backup is disabled.
- `app/src/main/proto/`: ESPHome protobuf definitions pinned to the upstream commit documented in its README and license; Java-compatible changes are documented there. Consult the current upstream `api.proto`, `aioesphomeapi`, and ESPHome protocol documentation before changing message handling.
- The MIT-licensed `com.stonygrey:torann:0.3.2` supplies Noise NNpsk0. Its authors state that it has not been independently audited. Do not introduce custom cryptography or silently downgrade to plaintext. Unencrypted connections must remain an explicit user choice with a warning. Never transmit credentials to another service or log secrets.

## Build and testing

- Run `./docker/build.sh`; it builds `docker/Dockerfile`, then runs `gradle --no-daemon testDebugUnitTest assembleDebug` inside Docker. APK: `app/build/outputs/apk/debug/app-debug.apk`.
- The persistent Gradle cache and debug signing key are in `${TMPDIR:-/tmp}/esphome-gradle-cache`. Deleting the cache can change the debug key and make in-place upgrades fail. Avoid removing the installed app or clearing its data without a good reason: it contains homes, device assignments, and saved keys.
- Unit tests include manual endpoint validation, plaintext framing, and a Noise client/server handshake and frame exchange. Extend tests for protocol changes, including malformed frames, actual upstream fixtures, and meaningful command/state behavior. The Noise loopback test alone does not establish real-firmware interoperability or audit security.
- A physical Samsung Android phone has previously been connected through ADB. If host ADB is unavailable, the image contains `/opt/android-sdk-linux/platform-tools/adb`. USB access has worked using Docker with `--privileged`, `/dev/bus/usb` mounted, and `/tmp/esphome-adb:/root/.android` for persistent ADB authorization. Device detection may require a retry. Install with `adb install -r` and preserve app data. Do not retrieve or display secrets when collecting device logs or UI state.
- Report exact build/test commands and results. Hardware tests should distinguish discovery, secure connection, live state, and actual command operation; do not assume one proves all the others.

### Web server interface

Device setup offers Native API (encrypted or unencrypted) and ESPHome web server (with or without username/password). `api/WebSession.kt` uses an HTTP event stream and REST commands; `ControlSession` unifies the initial dashboard entity types. Credentials are stored under separate Keystore-backed entries. HTTP must be explicitly selected and is not transport-encrypted, even when authentication is used; no connection silently falls back. Android's application-level cleartext policy is enabled to support user-configured LAN hosts and ports, so keep HTTP usage constrained to explicit web-server sessions and never log credentials. The client disables redirects, and supports Basic and Digest via `io.github.rburgst:okhttp-digest`. The server protocol and identifier formats vary by firmware; consult https://esphome.io/web-api/ and https://esphome.io/components/web_server/ before changing it.

Automated tests cover state decoding, select options and commands, SSE records, identifiers, command construction, public connections, Basic/Digest challenges and redirect behavior. A read-only real-device check confirmed a select entity and advertised options; the user’s setting was not changed during testing. A read-only check reached one real device's web event stream; app-to-device authenticated sessions and actual control commands still need physical-device verification. Existing Native API modes and keys must remain intact when editing or migrating devices.
