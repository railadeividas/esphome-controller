## Product and design

Build a local-first Android app that discovers and controls arbitrary ESPHome Native API devices directly, without Home Assistant, a cloud service, MQTT, or a required backend. Discover entities dynamically and use advertised capabilities and protocol message types, never infer controls from names. `screen1.png` and `screen2.png` are early visual references. Devices belong to the app and are each assigned to at most one location. Dashboards are separate and user-built (like Home Assistant dashboards): any number, one default, sections of entities from any devices, each with its own settings. Read-only values belong to the right of their entity names, aligned like control widgets.

## Implementation map

- Kotlin, Jetpack Compose, Android NSD, Gradle; application ID and namespace `com.example.esphomecontroller`. Minimum Android API 26, compile/target API 35. The current Noise dependency supports encrypted connections only on API 33+; keep that limitation explicit until a compatible implementation is verified.
- `app/src/main/java/com/example/esphomecontroller/MainActivity.kt`: activity and foreground discovery, serial NSD resolution, lifecycle and multicast lock.
- `LocationStore.kt`: devices belong to the app (stored once in the `devices` preference, each with an optional `locationId`); locations only organise devices. `DashboardStore.kt`: dashboards (preference `dashboards`, `defaultDashboard`), sections (`TILES`, `LIST`, `COMPACT`, `HEADING`; no Device type), `ItemRef(deviceId, stableId)`, per-dashboard `DashboardSettings`, templates and `DashboardCodec`. Also preferences and saved discovered addresses (SharedPreferences, not Room). `ConnectionManager.kt`: ViewModel owning per-device sessions for all of the app's devices while the app is visible, independent jittered backoff, network-change reconnects, setup errors, and the entity cache: last reported states stay in memory only (never persist states), while entity metadata (controls, capabilities, names, icons) and device details are saved by `ControlCache.kt` to `no_backup/control-cache.json` via `api/EntityCodec.kt`, so offline devices show their controls after a restart. A complete Native API listing (`entitiesComplete`) replaces the saved controls; web sessions only add.
- `ScreenHeader.kt` (shared page header), `AppScreen.kt` (shell, theme, navigation, dialogs, command-error snackbar), `SectionLook.kt` (section title colour and icon pickers), `MdiIcons.kt` (bundled Material Design Icons: `Mdi` index loaded once in the background by `LoadMdi()` in `AppScreen`, `Mdi.find`/`Mdi.search`, `MdiGlyph` draws a glyph from `res/font/mdi.ttf` at a fixed dp size; data in `assets/mdi/` built by `tools/mdi/build_index.py`, MDI 7.4.47, Apache 2.0), `Dashboard.kt` (Dashboard tab: dashboard switcher, sections, in-place edit mode, pull to refresh, summary, entity bottom sheet), `DashboardEditors.kt` (new-dashboard templates, section dialog, entity picker, settings sheet), `SettingsScreens.kt` (Settings list and its pages), `Screens.kt` (discover, devices, device page), `EntityViews.kt` (tiles, rows and per-platform controls), `DeviceSetupScreen.kt` (full-screen add/edit flow), `Discovery.kt` (TXT parsing, recommended mode). `api/Probe.kt`: one-shot read-only test connection (hello, device info, entity count) and key validation; `api/ConnectionErrors.kt`: `SetupException`s (key rejected, encryption required/not enabled, web credentials rejected) that stop retries and surface as setup errors.
- `api/Entity.kt`: typed model (`Platform` capabilities, `EntityState`, `Command`, `ConnectionState`), cache merge, command readiness and value formatting. `api/NativeProtocol.kt`: pure frame decoding to `NativeEvent`s, generic unsupported-entity listing from proto descriptors, and command construction. `api/DeviceSession.kt`: socket loop, handshake order (subscribe after `ListEntitiesDone`), keepalive pings and command dispatch; command failures go to `lastError`, never the connection state. `api/NoiseFrames.kt` and `api/PlaintextFrames.kt`: encrypted and plaintext framing. `api/SecretStore.kt`: Android Keystore-backed AES-GCM storage of device keys. App backup is disabled.
- `app/src/main/proto/`: ESPHome protobuf definitions pinned to the upstream commit documented in its README and license; Java-compatible changes are documented there. Consult the current upstream `api.proto`, `aioesphomeapi`, and ESPHome protocol documentation before changing message handling.
- The MIT-licensed `com.stonygrey:torann:0.3.2` supplies Noise NNpsk0. Its authors state that it has not been independently audited. Do not introduce custom cryptography or silently downgrade to plaintext. Unencrypted connections must remain an explicit user choice with a warning. Never transmit credentials to another service or log secrets.

## Build and testing

- Run `./docker/build.sh`; it builds `docker/Dockerfile`, then runs `gradle --no-daemon testDebugUnitTest assembleDebug` inside Docker. APK: `app/build/outputs/apk/debug/app-debug.apk`.
- The persistent Gradle cache and debug signing key are in `${TMPDIR:-/tmp}/esphome-gradle-cache`. Deleting the cache can change the debug key and make in-place upgrades fail. Avoid removing the installed app or clearing its data without a good reason or the user's permission: it contains locations, devices and saved keys. Saved settings have no migration code (the user accepted wiping during development), so a format change requires clearing app data.
- Unit tests include manual endpoint validation, plaintext framing, and a Noise client/server handshake and frame exchange. Extend tests for protocol changes, including malformed frames, actual upstream fixtures, and meaningful command/state behavior. The Noise loopback test alone does not establish real-firmware interoperability or audit security.
- A physical Samsung Android phone has previously been connected through ADB. If host ADB is unavailable, the image contains `/opt/android-sdk-linux/platform-tools/adb`. USB access has worked using Docker with `--privileged`, `/dev/bus/usb` mounted, and `/tmp/esphome-adb:/root/.android` for persistent ADB authorization. Device detection may require a retry. Install with `adb install -r --no-streaming` (streamed installs fail on this phone) and preserve app data. ADB sometimes drops the phone mid-install or when the screen is off; confirm with `dumpsys package com.example.esphomecontroller | grep lastUpdateTime` and retry. The user may be using the phone; avoid tapping through the UI while they are. Do not retrieve or display secrets when collecting device logs or UI state.
- Releases: every push to `main` runs `.github/workflows/release.yml` (tests, signed `assembleRelease`, GitHub release `vX.Y.Z` with the APK). Version name comes from Conventional Commits since the last `v*` tag (`.github/scripts/next-version.sh`), version code from the commit count; CI passes them as `-PappVersionName`/`-PappVersionCode`, plus `-PappBuildTime` (epoch ms, `BuildConfig.BUILD_TIME`, shown as "Build date" in About); local builds derive them from git and use the current time. Keep commit/PR titles in Conventional Commits form, since they drive the bump. Signing secrets are listed in `README.md`; without `ANDROID_KEYSTORE_PATH` the release build uses the debug key.
- Report exact build/test commands and results. Hardware tests should distinguish discovery, secure connection, live state, and actual command operation; do not assume one proves all the others.

**Connections**
- All of the app's devices connect while the app is visible; independent jittered backoff, network-change reconnects, keepalive pings. Wrong keys, encryption mismatches and rejected web credentials stop retrying and show "Fix connection settings". Failure reasons are mapped to short messages without addresses (`failureReason`).
- Discovery: Refresh-only 30 s scans with spinner/Stop; found devices persist (ViewModel) until the app closes; devices already in the app are hidden. Silent 15 s background scans run at start and when a follow-discovery device is unreachable, to refresh saved addresses.
- Setup: TXT-based pre-selection (`api_encryption` etc.), read-only Test connection before saving with specific errors, "Look up device" for manual addresses, inline key validation. Key provisioning over zero-PSK Noise was deliberately left out.

### Web server interface

Device setup offers Native API (encrypted or unencrypted) and ESPHome web server (with or without username/password). `api/WebSession.kt` uses an HTTP event stream and REST commands; `ControlSession` unifies the initial dashboard entity types. Credentials are stored under separate Keystore-backed entries. HTTP must be explicitly selected and is not transport-encrypted, even when authentication is used; no connection silently falls back. Android's application-level cleartext policy is enabled to support user-configured LAN hosts and ports, so keep HTTP usage constrained to explicit web-server sessions and never log credentials. The client disables redirects, and supports Basic and Digest via `io.github.rburgst:okhttp-digest`. The server protocol and identifier formats vary by firmware; consult https://esphome.io/web-api/ and https://esphome.io/components/web_server/ before changing it.

Automated tests cover state decoding, select options and commands, SSE records, identifiers, command construction, public connections, Basic/Digest challenges and redirect behavior. A read-only real-device check confirmed a select entity and advertised options; the user’s setting was not changed during testing. A read-only check reached one real device's web event stream; app-to-device authenticated sessions and actual control commands still need physical-device verification. Existing Native API modes and keys must remain intact when editing devices.
